## 核心解读

### 1. 背景与问题

当前 Agent 编排的事实标准是「让 LLM 边想边决定」：判断、生成、动作选择共用一次推理调用，输出是自然语言或半结构化文本。这套做法有三个系统性缺陷。其一，判断不可校验——消费端靠正则和 JSON mode 兜底，schema 漂移是常态。其二，判断不可比较——没有数值化置信度，路由逻辑只能硬编码在 prompt 里。其三，判断不可并行——判断嵌在推理链内部，只能串行等待，延迟随步骤线性累积。

前置知识有三块：结构化输出与 function calling；概率校准（calibration）与 ECE；传统系统里的推测执行（speculative execution）与幂等提交。这三者在后端世界里都是成熟概念，文章的价值在于把它们搬回 Agent 语境并重新组合。

### 2. 设计方案

文章的核心主张是分层：把「判断」从「生成」中拆出来，交给专门的 System One 模型——快、短、非文本、只做结构化判定；开放性的长推理仍交给常规 LLM。围绕这一点有三个机制构成一条流水线。

类型化决策：一次决策不是一段文本，而是一个有 schema 的类型化对象。决策类型一经定义，消费端（编排器、重试逻辑、审计链路）就能像消费 RPC 响应一样消费它，而不是去猜模型的措辞。

置信度校准：每个决策附带经过校准的置信分，而不是模型自报的「把握程度」。阈值因此变成可配置的路由参数——高于阈值直接提交，低于阈值升级到慢推理或人工确认。

推测性扇出：在分支密集的步骤，并行发起多条候选判断或动作，再依据置信度与后续验证结果决定提交哪一条，其余丢弃。

System One 模型在这里的角色类似控制面：它不回答「为什么」，只回答「属于哪一类」和「有多确定」。

### 3. 权衡分析

精度与延迟的 trade-off：把判定交给小模型能显著压缩单步延迟，但代价是准确率下降，必须靠校准与阈值路由把误差兜回来。这是典型的「用架构换模型能力」。

并行与成本的 trade-off：推测性扇出是用 token 换延迟。只有当分支多、单步成本低、失败可丢弃时才成立；一旦候选动作带副作用（扣款、发消息、写库），扇出就必须配合提交语义设计，否则并行的每一支都成了事故源。

类型化与灵活性的 trade-off：schema 收得越紧，泛化越差。遇到 schema 之外的意图时，系统必须有一条显式的逃逸通道（升级到通用推理），否则会被迫在类型定义里不断堆特例，最终退化成另一套 prompt。

校准的时效性：置信度校准隐含一个假设——数据分布稳定。线上分布漂移后，阈值会静默失准，且不会有任何报错。这是整套设计里最脆弱的一环。

### 4. 工程实践

落地时几个关键点：官方 SDK 支持异步调用，意味着判定可以嵌入现有异步编排器，作为一个普通 tool 调用，而不是外挂一层服务。幂等与提交语义必须显式设计——扇出产生的候选动作在提交前不应产生外部副作用。阈值应当作为配置项而非硬编码常量，并支持按决策类型分别设定。决策类型应当当作契约做版本管理，schema 变更等同于接口变更。可观测性上，最有价值的是记录（决策类型、置信分、实际结果）三元组，这批数据既能做在线 ECE 监控，也是回收再校准的唯一燃料。

## 架构师点评

第一，把「判断」定义为一种有类型、带置信度的资源，而不是模型输出的副产品，方向是对的。生产事故复盘里反复出现的一类问题，就是某个 Agent 在链条中段做出了错误判断却没有任何标记，直到末端才暴露。类型化决策让错误在发生点就可被观测、可被拦截。

第二，置信度校准是整个方案里最容易被低估、也最容易腐烂的部分。阈值一旦写死，就等于把线上质量绑死在离线校准时的分布上。任何在没有漂移监控的前提下上线这套设计的团队，都会在几周后收获一批「阈值还正常、结果已经错」的静默故障。

第三，推测性扇出的迁移性要打折看。它在读路径（检索、分类、路由、查询改写）上非常优雅，在写路径上则需要先有幂等原语和事务边界，否则并行只会把串行故障放大成并发故障。

第四，System One / System Two 的分层与后端里控制面/数据面的分离是同构的。这提示了一个更一般的判断：Agent 系统成熟的标志，不是推理能力的提升，而是决策接口的稳定化——什么时候该由快系统裁决，什么时候必须升级到慢系统。

## 延伸思考

如果我来做类似系统，会在三个地方与原文不同。

一是先定决策契约，再选模型。原文从模型出发推导用法，我会反过来：先把 Agent 全链路拆成有限的决策点集合（每个点定义 schema、阈值、升级条件、是否可扇出），再决定每个点用什么模型、跑在什么延迟预算里。模型是可替换件，决策契约才是长期资产。

二是把校准做成在线闭环而不是离线作业。落地形态是：每个决策点采样一小部分交由慢模型或人工复核，用结果持续重算置信分的实际命中率，偏移超限就自动收紧阈值并告警。没有这条回路的校准，本质上是一次性配置。

三是显式区分「判断正确率」与「判断代价」。原文关注决策本身的质量，但生产系统里两类错误代价完全不同：把不该提交的提交了，和把该提交的升级成了慢路径。前者是事故，后者只是成本和延迟。阈值设计应该按这两类错误的期望代价来定，而不是按一个统一的准确率指标。

原文没有充分展开的一点是：当决策点多到几十上百个时，谁来维护这套类型定义和阈值？这本质上是一个配置治理问题，答案通常不在模型侧，而在平台侧——决策类型的注册中心、版本化、灰度与回滚能力，才是这套设计能否撑过一年的分水岭。
