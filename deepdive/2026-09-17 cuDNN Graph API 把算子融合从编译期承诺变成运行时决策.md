## 核心解读

### 1. 背景与问题

逐算子 launch 的执行模型要交三重税：每个算子往返一次 global memory 的带宽税、kernel launch 的固定开销、以及跨算子优化机会的整体丢失。一个孤立的 elementwise epilogue 单独 launch，读写各一遍就是三倍带宽。而旧式库接口是"选算法"模型——一个不透明的 op 加一组 heuristics 挑出的默认实现，用户既看不到候选集合，也无法表达"把 conv + bias + 激活 + 残差融成一个 kernel"这种意图。

### 2. 设计方案

三段式：声明式图 → engine 枚举 → plan 物化。用户用 tensor（带对齐要求、允许虚拟张量）描述 DAG；运行时返回全部可行的 engine config（实现 × 配置：tile、split-K、CTA rasterization、数学精度、各类 knob）；再由 heuristics 或 benchmark 选出配置，finalize 成 execution plan，variant pack 绑定指针后执行。三个关键机制：runtime fusion engine 对匹配子图在运行时 JIT 生成融合 kernel（conv/matmul 加 epilogue、含 FP8 block scaling 的 SDPA 前反向）；feasibility check 在构建前筛掉不支持的对齐、形状、dtype、架构组合；plan 以 (graph, shape, device) 为键缓存。

### 3. 权衡分析

融合粒度 vs 占用率：融合越多，寄存器压力越大、occupancy 越低，收益是非线性的。手写 mega-kernel（FlashAttention 路线）能压到极致但只服务一个形状族；runtime fusion 覆盖"常见模式 + 通用形状"，用可维护性换取局部最优。JIT 编译延迟 vs 稳态性能：首次遇到某 shape 要付编译时间，成本从研发期搬到运行期，要么预热要么吞首帧毛刺。heuristics vs autotune：前者零成本但可能偏离最优一截，后者用 warm-up 墙钟换稳态吞吐——真正的问题不是选哪个，而是搜索空间必须有界，否则调优时间随形状组合膨胀。动态形状 vs 计划缓存：符号维度带来形状多态，缓存键空间爆炸，要么分桶要么接受 miss 时回退。确定性 vs 性能：换 engine config 就是换累加顺序，数值必然漂移，要可复现就得把候选过滤到 deterministic 实现，主动放弃一部分性能。

### 4. 工程实践

调优必须移到服务启动的 warm-up，用真实流量的代表形状跑一轮，结果按 (库版本, driver, 架构, SKU, 图哈希, shape) 落盘，miss 时回退 heuristics 而不是抛错。workspace 上限是必须显式设置的旋钮：融合与 split-K 的 workspace 需求差异巨大，放得太松会 OOM，收得太紧会静默选中慢实现。CUDA Graph 抓取要求指针稳定，动态形状意味着按 shape 实例化多份 graph。可观测性至少埋三个指标：融合命中率（子图未匹配即回退的比率）、plan 缓存命中率、单次调优墙钟成本。三者任一劣化，性能都会以无人察觉的方式下滑。

## 架构师点评

值得学习的一点：它把"怎么执行"变成可枚举、可选择、可缓存的一等公民。好的抽象不是把实现藏起来，而是把候选集合暴露成数据，让上层做决策。

存疑之处：文档强调能力矩阵，却很少交代回退行为。融合失败是静默降级为逐算子执行，性能可能掉一个台阶且没有任何信号——线上没有融合命中率指标，一次库升级就能让吞吐悄悄退 20%。

可迁移性：声明式图 → 候选枚举 → 计划物化这套骨架在 CPU/NPU 编译器上同样成立。端侧的关键差异是 JIT 不可得，调优必须离线化，实时路径只允许查表。

版本耦合是隐形成本：plan 缓存与库版本、驱动强绑定，升级即失效。把 plan 当配置工件入库、灰度对比，比运行时重新搜索可靠得多。

数值契约需要前置：engine 切换带来的结果漂移是事故高发区，FP8 block scale 下尤甚。把数值容差写进 plan 选择的约束条件，而不是留给下游测试去发现。

## 延伸思考

如果我来做，终点是"调优工件化"：离线在目标硬件上跑满候选，把选中的 plan、workspace 大小、数值容差一起固化进发布物，运行时只做查表与一致性校验；再加一层计划漂移检测，回退率或 p99 越过阈值即告警。

原文没提到但同样重要的是责任边界——调优结果由模型侧、编译器侧还是 SRE 负责。边界不清，每次库升级和机型切换都会变成一次事故。端侧还有一条硬约束值得写进设计：内存预算固定、workspace 不可增长，plan 选择必须在"内存可行集"而非"性能最优集"里完成。这一条往往决定了端侧引擎和 GPU 侧推理框架是两套设计，而不是同一套代码的两个开关。
