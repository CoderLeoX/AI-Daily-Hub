## 为什么选这篇

过去一年，Agent 工程最大的摩擦不在模型能力，而在「谁来管生命周期」。每个团队都在自建 ReAct 循环、会话存储、工具沙箱、重试与断点续跑，重复造轮子且难以稳定。OpenAI 这次把 Codex 的 harness 能力产品化，直接以托管服务形态提供编排、长时会话与工具调用——这是一次架构权力的重新划分：把编排层从应用侧的框架收编进平台运行时。它解决的正是「Agent 从 demo 到生产」的那道坎，且牵涉状态、沙箱、成本、锁定四重设计取舍，值得逐层拆解。

## 核心解读

### 1. 背景与问题

无状态推理 API 的抽象假设是「一次请求 = 一次答案」。Agent 打破了它：一个任务要经历规划、工具调用、观察、修正、再规划，可能跨越几分钟到几小时，中途还要等待外部系统。这本质上是持久化工作流（durable execution）问题，和 Temporal、Airflow 面对的是同一类难题——但 AI 应用普遍缺少成熟的编排基建。结果是每个团队都手写 while 循环，状态放在内存里，进程一挂全丢；工具执行没有隔离边界，凭据直接暴露；长任务没有成本护栏，token 账单失控。

### 2. 设计方案

从官方描述看，Agents API 的关键决策是：把「Codex harness」这一已被验证的编排实现，抽象成托管服务对外提供。分层上大致是——模型层负责推理；harness 层负责循环控制、计划推进与工具调度；会话层负责长时状态的持久化与续跑；工具层负责执行环境。开发者交付的变成两样东西：Agent 的行为定义，以及可被调用的工具集合。控制流不再由应用代码驱动，而是由运行时托管。这个抽象把「编排」从库（library）升格为服务（service），语义上更接近「你声明目标，运行时负责推进」。

### 3. 权衡分析

第一重取舍是控制权与可靠性。托管运行时换来了断点续跑和一致性保证，代价是循环内部的裁决权让渡——你想插入自研的路由、剪枝或验证逻辑，只能通过运行时开放的钩子，而非任意代码。第二重是耦合度：harness 与自家模型（尤其 Codex 系）的分布天然对齐，在 OpenAI 模型上表现最好，形成一种「软锁定」——不是 API 不兼容，而是调优红利只在自己家里兑现。第三重是长时会话的成本模型：把整个轨迹留在服务端，意味着状态复用的收益与「上下文膨胀」的成本同时被放大，长任务的经济性取决于缓存命中与摘要压缩策略。换一个数据主权敏感的场景（金融、医疗），托管路径可能直接不可选，自建编排仍是唯一解——这不是技术优劣，而是合规边界。

### 4. 工程实践

生产化真正吃力的地方在于四件事。其一，幂等：工具调用必须可重放，否则会话恢复会造成重复下单、重复发信这类副作用，写操作需要幂等键。其二，隔离：Agent 生成的代码/命令要在沙箱内执行，凭据通过代理注入而非直挂进程环境。其三，护栏：单任务 token 预算、最大步数、超时熔断必须显式设定，缺省值往往过于宽松。其四，可观测：长时任务的调试依赖完整轨迹回放——每一步的输入、工具结果、决策依据都要可检索，否则失败只能靠猜。运维视角还需灰度机制：Agent 版本变更等同于生产变更，必须有影子流量与快速回滚。

## 架构师点评

把编排做成托管服务，是正确方向的抽象升级。与当年「自建 Kubernetes」到「托管 K8s」的路径同构：绝大多数团队的编排实现不会成为竞争力，可靠性才是。交出控制面换来的是可预期的稳定性。

但「托管 harness = 可移植性下降」是真实代价。建议以 MCP 这类开放协议作为工具层的标准接口，把差异锁在编排层而非工具层——将来换运行时，工具资产不必重写。这也是 MCP 真正的战略价值：它保护的是你的资产，不是任何一家厂商的。

长时会话的状态管理最容易被低估。它会以「上下文成本」的形式复现，而且比无状态调用更贵——因为你想保留的信息恰好是最贵的部分。摘要压缩、轨迹裁剪、状态外置到自己的存储，这几件事迟早要做。

从 SRE 角度，Agent 的失败模式与普通服务不同：它不宕机，它「沉默地做错事」。所以可观测性的第一优先级不是延迟和错误率，而是决策轨迹的可审计性。没有轨迹的 Agent 运维，等于盲飞。

对国内团队的现实提醒：托管路线在数据出境与合规上通常不可行，但架构思想可以直接搬——把 harness 抽成独立服务进程，会话状态落到自己的持久层，工具走 MCP 网关。这套自建版并不难，难的是把它当基础设施而不是业务代码来对待。

## 延伸思考

如果我来做类似系统，会先划一条界：编排层是基础设施，业务 Agent 只是它的租户。具体而言——会话状态存自己的数据库（Postgres + 事件表），编排进程无状态、可水平扩展、崩溃即恢复；工具调用统一走内部 MCP 网关，网关负责鉴权、配额、审计与幂等；每步决策写入不可变的轨迹日志，作为调试与合规的唯一事实源；成本预算作为一等参数在会话创建时强制声明。

原文没展开、但生产中必然要面对的一点是：多 Agent 协作的失败模式。单 Agent 的失败是「做错」，多 Agent 的失败是「互相确认错误」——一个 Agent 的幻觉被另一个当作事实采纳，误差在拓扑中放大。因此多智能体系统里，验证者的独立性比数量重要得多：不要让同一个模型、同一份上下文既当执行者又当裁判。这需要架构上的隔离设计，而不是提示词上的约束。

另一个被忽视的问题是可测试性。Agent 系统的回归测试不能只靠人工抽查，需要把历史轨迹沉淀为可回放的评估集，每次 harness 变更跑一遍。没有这一步，「一劳永逸」就只是愿望——每次升级都在赌。
