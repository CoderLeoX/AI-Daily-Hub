## 核心解读

### 1. 背景与问题

费马大定理由费马 1637 年提出，直到 1994 年才由 Wiles 借助模性定理完成证明，论证繁复。而"形式化证明"意味着把整条证明链送入证明助手，从公理出发每一步都由机器校验，不存在"显然"和省略——对 LLM 而言这是最苛刻的任务类型：普通评测是生成答案，这里是要生成可执行、必须通过编译的工件，一次幻觉就是一次编译失败。此前以 Lean/mathlib 为代表的社区已形式化大量当代数学，但 FLT 这类"世纪定理"长期被视为禁区：规模大、依赖深、非专家无法判断进展。此次"首个完整形式化证明"因此不只是 AI 里程碑，更是对验证闭环 Agent 能力的试金石——而过程并不顺，"靠 Harness 救回来"这句细节，比结果更值得工程师读。

公开信息可确认的有限：由姚班背景研究者主导、以 Claude 为推理引擎、借助 Harness 编排完成全链形式化。从架构视角，此类系统必然包含四层（属通用设计推断，非原文细节）：分解层，把 Wiles 证明拆成可独立验证的引理子任务；生成层，模型产出定义与证明脚本；验证层，证明助手即时返回类型错误与未闭合目标，形成高频闭环；编排层即 Harness，维护子任务状态、失败重试、上下文回收与全局进度，相当于长任务的操作系统。摘要特意点出 Harness 在最后阶段"救场"，恰好说明：决定成败的确定性逻辑——何时暂停、恢复、换策略、重启哪段——全部沉淀在编排层，而非模型 prompt 里。

### 3. 权衡分析

三个关键 trade-off：其一，全自动 vs 人机协同。纯模型闭环对世纪级任务仍不够稳，最终以研究者 + Harness 的半监督方式收尾，人类只做"方向性仲裁"，不做机械步骤——这是成本与可控性之间的合理落点。其二，上下文当状态 vs 显式状态。若让模型在对话里记住整条证明链，必然上下文爆炸且无法恢复；Harness 把状态外置到文件、检查点与任务队列，模型只持有工作集。这正是"最后救回来"的技术原因，也解释了为什么 Agent 应用里编排比提示词重要。其三，一次长跑 vs 分而治之。整条证明单线程生成不可行，必须先产出依赖图；但分解本身依赖对证明的理解，是典型的"分解者困境"。换场景看：失败代价低的浅任务不需要这套重编排；而一旦没有自动验证器，闭环退化为模型自我评估，可靠性断崖式下降——证明领域恰因硬裁判存在，成为 Agent 最肥沃的土壤之一。

### 4. 工程实践

对工程师最直接的借鉴，是把"证明"替换为"代码变更"：证明助手 ≈ 类型检查 + 单测，每次编译失败都是一次确定性反馈，无随机、无模糊——本质是 CI 的 Agent 化。落地要点有四：断点续跑与幂等（长任务必挂，恢复粒度直接决定成本）；上下文预算管理（大状态外置，模型只持工作集）；全量审计留档（每一步生成物可复盘，失败分布是调优依据）；成本配额（验证器空转与模型重试都是钱，需设上限）。SRE 视角下，这类负载是典型"高方差长事务"，要像调度批处理一样管理优先级、重试上限与人工审批闸门。最后是信任边界：机器校验保证了逻辑链，不保证产物对人类可用——交付物能否沉淀为可读文献，是另一件事。

## 架构师点评

最值得学的是"硬裁判前置"。Agent 可靠的唯一路径，是让错误被廉价、确定性地发现；Lean 这类工具把幻觉从隐性变成编译错误。凡能建立 ground truth 的领域——代码、形式化、DB schema——Agent 化的优先级应该最高，这是本文对全行业最可迁移的结论。

Harness 即操作系统：模型是 CPU，编排是内核。状态外置、检查点、恢复、调度——长任务 Agent 的成败不在单次推理质量，而在编排的确定性。"最后靠 Harness 救回来"是对"堆模型能力就能解决一切"最直接的证伪，也是对本周同池"人人都能自建 Harness"话题的呼应：框架层正在商品化，稀缺的是把它用好的系统能力。

存疑处在于成本与可复现性。世纪级证明的一次性长跑，算力、token、人工校核的总消耗若不可复现、不可规模化，里程碑意义会被稀释。原文未给成本曲线，读者应警惕"demo 成功 ≠ 工程可行"，这也是此类新闻常见的失真点。

注意迁移边界。该范式成立的前提是：存在形式化目标和现成数学库。落到业务 Agent，若任务没有自动验证器，应先造"弱裁判"——lint、测试、合同校验——再谈编排；否则闭环断裂，Harness 也无从救场。
