## 架构师点评

一、并发数不是 Agent 系统的核心指标，验证带宽才是。可借鉴的做法是把生成侧当无状态、可重试、可丢弃的算力，把验证侧当有状态、确定性、必须可重放的关键路径。两者性质不同，不该共用同一套调度语义。

二、"不能排除"是一种技术债。当训练、推理、用户会话共用一个数据平面时，"是否污染"这个问题在架构上就无法确定性回答，只能靠事后声明。这跟日志与审计缺失是同一种债，只是后果更贵。

三、溯源应当默认开启。原文最有价值的不是那份证明，而是暴露的缺口：模型看过什么、数据来自哪里，必须是可查询的状态位，而不是公关口径。

四、规模只在有 oracle 的领域线性收益。一万个 Agent 对齐一个数学目标容易，因为目标可验证；目标是产品需求或架构演进这类不可验证物时，同样的并行只会生产分歧。可迁移性有明确边界。

五、存疑之处：原文未说明证明是否经过形式化检查，也无第三方复现，结论强度受限于声明本身。这是报道层面的事实，不影响其作为工程案例的价值。

## 延伸思考

如果我来做这套系统，会先设计验证器和调度器，再设计 Agent。三层拆分：搜索层（无状态 Agent，候选写入不可变存储）、验证层（形式化 checker 或独立的强 critic，确定性、可重放）、溯源层（每个候选记录 prompt 哈希、上游上下文来源、是否触及用户数据的标志位）。
