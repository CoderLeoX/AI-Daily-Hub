## 核心解读

### 1. 背景与问题

推理负载的功率曲线与 Web 服务完全不同：它不是均值的、可预测的，而是长尾加突发。连续批处理的目标是把 batch 填满以提高 GPU 利用率，但"填满"的物理后果就是打满功耗——利用率与功率几乎线性相关，这意味着一味追吞吐必然撞上电力和散热的天花板。风冷机房的单柜散热能力通常在 20-40kW 附近见顶，而当前一代超节点单柜已到 120kW 量级，公开路线图上的后续架构还在往上走。供电侧同样吃紧：传统交流到 54VDC 的多级转换在数百千瓦机架里会产生可观的铜损与转换损耗，因此向更高直流母线电压迁移成为必然。核心矛盾不是技术做不到，而是节奏错配：计算架构约 12-18 个月迭代一次，而数据中心供电与制冷改造周期是 3-5 年，两者天然对不齐。原文要解决的正是这种错配——让基础设施侧有可对齐、可采购、可验证的规格。

### 2. 设计方案

DSX Ready 的思路不是发布一款产品，而是建立一套资格框架：把功率与散热产品按能力分层，明确其必须匹配的计算架构与机架形态，让 builder 在采购阶段就能把热设计功耗、冷却介质、供电电压、机架密度这几件事对齐。它真正的贡献是把"设施-IT 协同设计"从一次性项目制，变成产品化、可复用的参考设计。类比电源的 80 PLUS：认证本身不提升性能，但把隐性风险转换成可比较、可采购、可签合同的公开参数，从而把"装完才发现不匹配"的返工风险消灭在图纸阶段。

### 3. 权衡分析

第一组权衡是液冷与风冷。液冷抬高散热上限、改善 PUE，代价是漏水风险、快接头等新增故障点、CDU 与二次侧回路的可靠性单点，以及存量机房的改造成本。第二组是供电制式。高压直流减少转换级数与铜损，但生态不成熟、备件受限、运维人员不熟悉，保护器件选型也更复杂。第三组是容量配置：按峰值配置安全但极贵，且会长期压低真实利用率；按均值配置加突发限制便宜，代价是高峰期降频，把不确定性转嫁给线上延迟。第四组是标准化的双刃剑：认证收敛降低集成成本，但可能把选择权让给单一生态。换场景看，若负载是可预测的离线批处理，功率削峰空间大、均值配置可行；若是延迟敏感的在线服务，batch 被压小、功率波动剧烈，对制冷的动态响应要求反而更高。

### 4. 工程实践

落地层面有几件事必须做。其一，显式设置功率上限换取可预测性，用实测的吞吐-功率曲线决定裁剪点，用可控的吞吐损失买稳定性。其二，监控不能只看 GPU 利用率，必须有每机架功率、进出水温度、CDU 流量与压差、以及降频计数器；降频事件要单独告警，因为它是"看起来没坏但已经在亏钱"的典型形态。其三，部署分期，先小规模验证二次侧，保留风冷机架做混合与灰度。其四，把 PUE 与 WUE 纳入 SLO，液冷快接头纳入备件与演练。其五，扩容前先算电：IT 功率、PUE、制冷余量、UPS 容量必须是一本一致的账。

## 架构师点评

一，把物理约束写成选型准入参数，是典型的故障左移。这套思路完全可以搬到软件层：给推理服务定义"降频率、尾延迟、每瓦 token 数"作为上线准入测试，不达标不许进生产。

二，存疑之处在于生命周期对齐。认证绑定计算架构，而架构 12-18 个月一变，基础设施折旧却是 3-5 年，中间这几年的错配成本由谁承担？原文没有回答 TCO 与代际兼容问题，而这恰恰是自建方最关心的。

三，可迁移性强。任何资源受限的部署——包括单机低功耗卡本地推理——本质都在做同一件事：先钉死资源上限，再优化单位资源产出。策略同构，只是尺度不同。

四，对国内不宜照搬。大量存量机房仍是低功率密度架构，电费与改造成本占比更高，现实路径往往是"低功耗卡 + 更激进的量化 + 更高机架复用"，即牺牲单卡峰值换密度与电费。

五，真正的杠杆是利用率而非峰值。当功率成为瓶颈，调度器就该功率感知——按瓦特调度，而不是按卡数调度。

## 延伸思考

如果我来做，第一件事是把 watt 变成一等调度资源：在编排层像申请 CPU/内存一样申请功率预算，连续批处理的目标函数从"最大 batch"改成"每瓦 token 数"。第二件事是建立 token/Watt 指标并纳入月度评审，让容量决策有数据而不是有直觉。第三件事是预留电力余量作为突发缓冲，而不是把它当成常态超配。

原文没提到但重要的有三点。其一是共享基础设施的故障域与热耦合：一个 CDU 服务多租户时，噪声邻居会以温度的形式出现，这是新的隔离问题。其二是硬件淘汰时的回路复用与冷媒、水处理的环保合规，长期看会变成硬约束。其三是软件层的反制手段——KV Cache 分层卸载、prefill/decode 分离、投机解码，这些能在不增加一瓦的前提下提高吞吐，是与硬件解耦的真正杠杆。在电力受限的现实里，异构调度（把长尾请求丢给低功耗卡）很可能比再买一批高端卡更划算。
