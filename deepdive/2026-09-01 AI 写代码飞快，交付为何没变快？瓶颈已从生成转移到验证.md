## 核心解读

### 1. 背景与问题

交付链路是：理解需求→定位改动点→生成代码→自测→集成→评审→回归上线。引入 agent 后，只有"生成"的边际成本趋近于零，其余环节成本原封不动。过去"写代码慢"像掩体，掩盖了其他环节的低效；生成被加速后掩体消失，瓶颈显式化：上下文准备、正确性验证、评审带宽、存量兼容。本质是典型的系统瓶颈问题：吞吐不取决于最快的环节，而取决于最慢的环节——只是此前没人把它当系统问题看。

### 2. 设计方案

生产级实践的共性架构是"规划—检索—执行—验证"四层闭环，而非单 agent 直出代码。规划层把需求拆成可验证的变更任务；检索层用仓库级索引（符号、调用图、历史提交）定位相关代码，把"找对文件"从模型能力变成系统能力，避免全库塞进上下文；执行层在沙箱里改代码、跑命令，副作用可回收；验证层把测试与静态检查设为强制关卡，不过就带着失败信号回去改。核心约束只有一个：没有验证信号的生成不算完成。评审与合并作为人工兜底留在环外，形成"机器完成、人做判断"的分工。

### 3. 权衡分析

最关键的 trade-off 是自动化程度与错误成本的交换：全自动合并吞吐最高，但一次静默错误变更的代价可能吃掉整周收益；半自动把验证负担转嫁给 review 带宽——而这正是交付链路最稀缺的资源。其次是上下文策略：全量注入省掉检索系统，但窗口膨胀、注意力稀释、成本线性上升；检索注入依赖索引新鲜度，索引过期产生的是比漏检更隐蔽的错误检索。再者是验证粒度：全量测试让"快"的生成重新慢下来，针对性测试依赖影响分析的准确度，分析不准就是漏测。三组权衡本质是同一个选择：复杂性与成本放在系统哪一层。低风险场景（脚本、文档）可把自动化旋钮调到接近全自动，核心交易代码必须保留强人工闸门——自动程度应按变更风险分档，而非一刀切。

### 4. 工程实践

实现层面三件事决定成败。一是沙箱与变更粒度：执行必须隔离、可回滚，一次只产出一个可独立评审的变更，否则故障无法归因。二是可观测性：每步的 token 消耗、耗时、重试、失败模式都要留痕，否则回答不了"钱花在哪、时间去哪了"，经济性论证无从谈起。三是错误预算：agent 的典型失败不是崩溃，而是"礼貌地完成错误任务"，必须有抽样复核与错误率指标，超预算即降级自动化。运维视角还有个常被忽视的点：交付慢的瓶颈往往不在 agent，而在 review 队列长度与测试等待时间——这两个正是 SRE 能直接量化、直接优化的对象。

## 架构师点评

值得学习的是问题定义：把"AI 编码效果"重新表述为"交付链路的吞吐与延迟分解"，用瓶颈分析代替能力崇拜。这个抽象适用于一切 agent 系统。

依赖人工 review 兜底，说明验证信号还不够强。下一步不是更快生成，而是把"测试通过"升级为"行为契约＋语义等价"验证，把正确性责任前移到机器侧。

检索层是新的失效点：索引过期、检索偏差比模型幻觉更隐蔽，且没有现成监控。需要为检索质量建独立评估集，持续回归。

架构可迁移：规划—检索—执行—验证的分层对运维 agent、客服 agent 同样成立，"验证闭环"是唯一不可省略的约束。
