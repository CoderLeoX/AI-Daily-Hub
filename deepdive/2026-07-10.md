─── 【为什么选这篇】 ───

本周候选池中，多数为模型发布或人事新闻，缺乏可拆解的系统设计。InfoQ 的这篇《Agent 进化论》直接切入本周「Agent 系统工程」主题：从单轮对话到多步骤协作，背后涉及工具调用编排、状态管理、记忆持久化、多 Agent 通信协议等架构决策。原文并非产品 PR，而是梳理了工程演化路径和关键设计权衡，有实质的技术干货可提炼，对国内一线工程师构建生产级 Agent 系统有直接参考价值。

─── 【核心解读】 ───

**1. 背景与问题**  
原文首先拆解了 Agent 的「对话瓶颈」：传统 LLM 对话缺乏状态保持和工具执行能力，无法完成多步任务。当 Agent 需要依次调用搜索、数据库查询、代码执行、外部 API 时，单个模型推理必须依赖额外编排层。核心矛盾在于：模型自身的 reasoning 能力（CoT/ReAct）与系统层面的执行可靠性、可观测性之间的 gap。作者指出，当前 Agent 正处于「从单次对话工具调用，向持续协作工作流」的转折点，这在架构上要求从「无状态 prompt 链」转向「有状态任务图」。

**2. 设计方案**  
原文梳理了三种演进方案（我归纳为三个阶段）：  
- **阶段一：ReAct 模式**。模型在单轮中交替推理（Thought）和行动（Action/Observation），依赖上下文窗口维持状态。优点是实现简单，但上下文错位、工具结果溢出、长链执行不可控是致命伤。  
- **阶段二：编排器 + 工具注册中心**。引入 Agent Runtime，将工具注册、参数校验、结果回填从模型推理中解耦。代表如 OpenAI Function Calling 和 Anthropic Tool Use，但原文指出这类方案仍是「模型驱动执行路径」，缺少分支和并行。  
- **阶段三：有向无环图（DAG）+ 任务调度器**。Agent 工作流被显式建模为 DAG，节点是原子操作（LLM call、工具执行、条件判断），调度器负责并发执行、重试、超时。这一阶段开始引入「协作」语义：多个 Agent 实例可被分配不同子图，通过事件总线交换中间结果。

**3. 权衡分析**  
原文的核心 trade-off 在于**表达力 vs 可靠性**：  
- ReAct 模式表达力最强（模型自由选择下一步），但执行路径不可预测，回溯和调试困难。  
- DAG 模式牺牲了「模型自由度」，但获得了确定性：执行计划可见、可中断、可恢复。对生产系统而言，这种确定性远比模型偶尔的灵光一现重要。  
- 另一个 trade-off 是**状态持久化粒度**：是每次工具结果写回上下文（低成本但易截断），还是由运行时维护 KV store（高成本但可跨会话）。原文倾向于后者，指出长期记忆必须独立于模型上下文。  
- 多 Agent 协作时的协议选择也值得注意：是让 Agent 通过自然语言互相通信（灵活但不可控），还是定义结构化消息（JSON-RPC / MCP 资源访问），后者是工程实践的主流。

**4. 工程实践**  
原文未详述具体部署，但可推导出关键实践点：  
- **错误处理**：工具调用可能超时、返回异常或不一致。运行时层需实现 graceful degradation：区分「可重试」（网络错误）和「不可重试」（参数格式错误），避免盲重试。  
- **可观测性**：Agent 执行轨迹（trace）必须包含每一步的 LLM prompt、工具输入输出、分支条件。原文建议引入 OpenTelemetry 风格 span，便于根因分析。  
- **会话隔离**：多 Agent 共享运行时需要租户隔离，避免跨 Agent 状态污染。容器级别隔离或进程级沙箱是常见选择。  
- **热更新**：工具注册和 Agent 行为策略需支持运行时动态替换，不能因新工具上线而重启所有 Agent 实例。

─── 【架构师点评】 ───

- **原文的最大价值是明确了「确定性优于灵活性」的设计原则**。很多团队初期迷信 ReAct 的「智能感」，在实际业务中却发现不可控率高达 30%+。将执行路径显式建模为 DAG 并从运行时剥离模型决策，是生产级 Agent 的必修课。

- **缺少对「Agent 记忆架构」的深入讨论**。原文提到了持久化但未区分短期工作记忆（当前任务上下文）和长期知识（用户偏好、领域事实）。前者应在运行时内存中管理，后者需独立向量库。两者的衔接是当前 Agent 系统最大的工程坑：简单拼接会导致检索噪声污染推理。

- **多 Agent 协作的「协议成本」被低估**。Agent 间如果通过自然语言交换中间结果，每次推理都是 O(n²) 的 token 消耗。结构化消息（如 MCP 资源/工具定义）虽能降低开销，但要求所有 Agent 注册同一套 schema，这本身对异构系统是强约束。原文未讨论 schema 演化和兼容性问题。

- **可迁移性高**：文中提出的「编排器 + 任务图 + 工具注册中心」架构，不仅适用于知识工作 Agent，也可直接平移至工业控制（边缘设备上的多步骤指令链）和测试自动化（Agent 执行测试计划）。核心是抽离 runtime 与 LLM，将执行引擎做成通用组件。

─── 【延伸思考】 ───

如果让我设计一个面向生产的多 Agent 协作系统，我会在原文基础上补充三点：  

1. **分层状态管理**：不做「一刀切」的状态存储。Runtime 层维护一个轻量级工作内存（in-memory hashmap，TTL 与任务生命周期绑定），仅在关键决策点（如跨 Agent 移交）持久化到 Redis / etcd。这避免了全量序列化导致的延迟，同时保住了故障恢复能力。  

2. **工具调用的「退化协议」**：不能假设所有第三方 API 都稳定响应。为每个工具注册一个 degraded handler（如搜索结果不可用时改用缓存或 fallback LLM 生成），运行时自行选择。这比在 Agent prompt 里写「如果取不到就换个方式」可靠得多。  

3. **Agent 幂等性设计**：原文未提重试的副作用。工具调用（如邮件发送、支付扣款）可能是非幂等的。应在运行时层维护「已执行命令」的 dedup set，结合 exactly-once 语义。LLM 生成的 action 永远存在幻觉，不能由模型层保证幂等。  

总的来说，Agent 从对话进化到协作，核心不是模型变强，而是**工程基础设施的成熟度比拼**。谁先建好可靠的运行时、可观测性和状态管理层，谁就能把 Agent 从 demo 送进生产。
