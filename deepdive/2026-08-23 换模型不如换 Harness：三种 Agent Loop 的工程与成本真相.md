## 核心解读

### 1. 背景与问题

Agent 开发正处在范式分叉点：模型能力差距在收敛，而同样的模型配上不同的循环工程，落地效果差异显著。核心挑战在于——agent 不是一次推理，而是一个"感知→决策→行动→观察"的循环，每一轮都在消耗 token、时间和出错概率。多数团队的注意力全放在模型上，忽略了循环本身的设计：工具调用怎么组织、上下文怎么管理、失败怎么恢复、副作用怎么控制。原文要纠正的正是这个认知偏差：harness 工程文献反复指向一个结论——决定成败的往往是模型外面那层循环，而非模型本身。

### 2. 设计方案

原文把运行 Agent Loop 的方式归纳为三种路径，并分别拆解其工程形态与成本结构：

路径一是手写直连循环：直接调用模型 API，自行实现工具调用协议、重试、上下文截断。成本结构最透明，但状态管理、并发、可观测性全部自建，死循环、上下文溢出等失败模式都要自己兜底。

路径二是框架编排：用 LangGraph 这类图/状态机运行时把 loop 显式建模，节点、边、检查点、人工介入点全部可控，可复现、可回滚；代价是引入抽象层，抽象泄漏时排查更深。

路径三是托管运行时：把整个 loop 交给平台，换来开箱即用的追踪、沙箱和配额，牺牲的是控制权与成本透明度。

经济学层面，同样的任务在不同 provider 上的 token 单价、缓存命中率、限流粒度、工具调用延迟各不相同；loop 越长，每轮上下文膨胀与缓存失效对总成本的放大越明显。这正是"供应商经济学"的核心：模型单价只是表象，loop 形态决定真实账单。

### 3. 权衡分析

三组核心 trade-off：

控制权 vs 开发速度。手写循环对行为与成本完全可控，但所有工程问题自担；框架内置了常见模式，却把调试成本转移到抽象层。选择依据是团队规模和任务风险，没有绝对优劣。

模型无关性 vs 供应商锁定。harness 把决策策略与模型实现解耦，换来跨 provider 迁移的自由——哪家便宜用哪家——代价是工具调用格式与行为差异需要一个持久维护的适配层。

上下文质量 vs 成本。长 loop 下，压缩、裁剪、摘要三种策略直接对立于省钱与保质量，这是 loop 设计中最核心的张力，且没有静态最优解，只能按任务实测。

换场景结论立即不同：短平快的单轮工具调用，手写循环最优；几十步的长 horizon 任务，检查点与状态持久化是刚需，框架优势明显。原文的价值在于给出了定位框架，而非标准答案。

### 4. 工程实践

实现层面可直接借鉴的细节：

- 把 loop 参数化：max_steps、超时、重试退避、幂等工具设计，是线上稳定的基本盘；
- 上下文预算管理：按 token 预算裁剪历史、截断工具输出、必要时摘要化，防止长任务"慢性失忆"；
- 成本护栏：为每个 loop 设 token/费用上限——loop 成本是"每轮成本×轮数"，两个维度都要监控；
- 可观测性：记录每步的 prompt、工具调用、耗时与 token 消耗。实际瓶颈常常是工具延迟与缓存命中率，而非模型延迟，没有 trace 就无从定位；
- 回归基线：用 Terminal-Bench 这类基准为 harness 建立基线，改 harness 先跑基线再 A/B，杜绝凭感觉调参。

## 架构师点评

值得学习的是认知纠正：把"模型选择"降级为次要决策，把工程重心放到 loop 上——这与传统系统"框架选型不如架构设计"同理，是对团队注意力的正确引导。

可借鉴的是可度量：用标准基准对 harness 做 A/B 而非凭感觉调 prompt。可度量是工程化的前提，这条经验可以直接移植到国内团队的 Agent 质量体系建设。

存疑之处：三种路径是理想化分类，现实多是混合形态——手写循环里嵌框架、托管运行时上再包一层。分类的意义在于帮助定位控制权与成本，而非非此即彼的教条。

局限：harness 的效果依赖任务分布与模型代际，Terminal-Bench 是终端任务域，结论迁移到检索、办公自动化等场景需要重新验证，不能直接外推。

可迁移性最强的是经济学框架：国内 API 的计价、缓存、限流策略差异更大，同样的 loop 在不同 provider 上成本可能差数倍，选型时必须把 loop 形态纳入成本模型，而这一点绝大多数选型评审都没做。

## 延伸思考

如果我来做类似系统，会把 loop 当作一等公民的系统组件而非 prompt 的附属品：定义统一的 Loop 接口（step、checkpoint、interrupt），让 harness 可插拔、可回归测试；把状态持久化做成默认能力——长任务崩溃可恢复，这是 SRE 视角的刚需，原文着墨不多；为工具层强制幂等与补偿设计，agent 的副作用（发消息、写数据）一旦重复执行就是生产事故，工具契约比 prompt 更重要。

原文没提但生产必答的三件事：多租户配额与隔离（一个失控 loop 不能拖垮全平台）、agent 的安全边界（它能触达哪些系统、以什么权限）、完整审计日志（每一步决策可回放）。这三项决定了 agent 能否从 demo 走到生产——而这恰恰是架构师和 SRE 真正要负责的部分。
