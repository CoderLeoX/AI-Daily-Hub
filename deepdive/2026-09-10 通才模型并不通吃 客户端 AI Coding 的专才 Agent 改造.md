## 核心解读

### 1. 背景与问题

客户端工程让"一个 Agent 干完所有事"的模式率先失效。代码量大、模块依赖深，通才 Agent 要同时承担需求理解、跨文件定位、编辑、构建验证，系统提示词只能越堆越长；上下文塞满无关模块后，模型开始丢失关键约束，工具调用随之失控——频繁触发分钟级构建、在错误的文件上做修改。更要命的是不可评测：一次失败无法归因是模型能力不足、上下文缺失还是编排失误，团队只能凭感觉调 prompt，没有工程可言。核心矛盾在于：通才模型的"全知"姿态，配不上工程任务天然的结构化分工。

### 2. 设计方案

分享给出的路线是"按职责拆 Agent，用契约串流水线"。入口由路由层做意图分类，把任务派给不同专才：负责检索与代码理解的、负责 UI 改动的、负责修构建与测试的、负责独立评审的。每个专才持有被裁剪过的专属上下文和专属工具集，而非共享一份完整会话；Agent 之间不直接对话，通过工作区文件与结构化消息传递产物。验证不再是 Agent 的自觉行为，而是 Harness 里强制的闭环：编辑完必须过静态检查与构建，失败即回传。整体架构从"一个模型循环"变为"调度器加分工流水线"，每类专才都能单独评测、单独换模型、单独回滚。

### 3. 权衡分析

拆的收益是确定性：单任务成功率可度量，失败可归因，模型升级风险被隔离——评审 Agent 换模型不影响编辑 Agent。代价是系统复杂度前移：路由本身成为新的错误面与幻觉面，分类错了后续全错；上下文切分是高危操作，该给的信息没给，专才再强也白搭；多次调用的延迟与成本上升，多 Agent 改同一文件还引入一致性问题。trade-off 的适用边界很清楚：任务越重复、越可评测、工具副作用越重，拆分越划算；长尾探索型任务与中小代码库，通才加一个好 Harness 仍是更优解，强行拆分是负优化。客户端工程还多一层约束：构建反馈以分钟计，逼着方案把"离线静态预检"做进 Harness，用廉价信号先挡掉大部分错误。

### 4. 工程实践

落地顺序比架构更关键：先固化 Harness 与评测集（用历史 Badcase 和 PR 做黄金样本），再谈拆分，否则拆完没有度量手段。上下文预算要显式管理，大型仓库不可能全量进上下文，靠检索与代码图谱把相关文件定向喂给对应专才。工具调用必须幂等、超时、限频，防止 Agent 反复触发昂贵构建；并发写文件需按模块划分职责或串行化。最容易被忽略的是可观测性：记录路由决策、每个专才的输入输出与工具轨迹，失败才能定位到"路由错、上下文缺、模型弱"三层中的哪一层。上线走灰度，先放补测试、修编译这类低危任务，再逐步放开重构等高危场景；所有失败样本回流扩充评测集，否则系统会随代码演进悄悄退化。

## 架构师点评

最值得学的是"先 Harness、后拆分"的顺序：先把不可观测的模型循环变成可评测的流水线，再用数据决定拆什么。这是把 Agent 当系统治理、而非当模型调教的正确姿势。

拆分边界应来自失败聚类而非职能想象。按"理解/编辑/验证"拍脑袋分工，不如先跑通才基线、统计失败模式再切；否则只是把幻觉从模型层搬到了路由层。

存疑点：专才数量会膨胀，每个专才都要维护专属上下文策略与评测集，团队容易被"Agent 运维"淹没。应定期度量每个专才的增量收益，不达标的合并回通才。

可迁移性强：客服工单、运维巡检这类"高频、可评测、工具重"的场景可照搬同一条路径。门槛在于必须有足够历史样本与闭环反馈——这决定了它只适合已有成熟工程流程的团队，从零搭流程者慎入。

## 延伸思考

如果我来做，会反着设计：不预设职能分工，先让一个通才 Agent 配固定 Harness 跑两到四周，把失败按根因聚类，用数据决定拆哪几个专才——拆分应该是涌现的，不是规划的。专才之间共享的不该只是任务产物，还应有一层工程记忆：架构约定、历史决策、踩坑记录，沉淀为可检索的知识库，而不是继续堆 system prompt。原文未展开但同样致命的是评测漂移：代码库在演进，黄金集半年后就失真，必须让生产失败样本自动回流并每周回归，否则"专才更稳"会悄悄退化成"专才更僵"。最后补一句通用判断：任何多 Agent 系统，反馈延迟决定编排策略——构建反馈一分钟和十秒的场景，调度设计完全不同。
