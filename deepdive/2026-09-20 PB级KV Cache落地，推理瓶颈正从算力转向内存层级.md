## 核心解读

### 1. 背景与问题

自回归推理分两段：prefill 是算力密集（矩阵乘满血），decode 是访存密集（每步只算一个 token，却要把全部历史 KV 读一遍）。KV 大小随上下文线性膨胀，公式大致是 2 × 层数 × KV 头数 × head_dim × 序列长度 × 批大小 × 精度字节。上下文推到十万级、批并发放大后，KV 从"顺手存显存"变成"显存装不下"。行业既有做法是省着用——GQA/MQA 减头数、PagedAttention 消除碎片、前缀缓存跳过重复 prefill。这篇文章的信号是反方向的：既然省不下来，那就把它放到更大的层级里去。PB 级意味着 KV 不再属于单卡、单节点，而属于整个数据中心的可寻址存储。

### 2. 设计方案

核心抽象有三步。第一，把 KV 从"序列的副产品"提升为"独立寻址的资源"——以 block 为粒度管理，用前缀 token 的哈希做键，命中即跳过 prefill。第二，分层：HBM → 主机 DRAM → 本地 NVMe → 分布式存储/对象存储，越往下越大越慢。第三，解耦：prefill 与 decode 分池部署，KV 通过高速互联在池间搬运，"超节点"在这里的真实作用是当缓存总线的角色。关键设计判断是——把缓存放到计算附近，而不是把计算搬到数据附近。这与 CDN、CPU 多级缓存完全同构：容量与带宽不可兼得时，用局部性换收益。

### 3. 权衡分析

第一，容量/带宽/成本三角。SSD 便宜但每 step 全量读 KV 的带宽需求极高，所以分层缓存只在"跨请求复用"时划算——多轮对话、Agent 长系统提示、RAG 公共语料。一次性长请求反而更贵：省下的 prefill 算力抵不过 SSD 延迟带来的 P99 恶化。第二，命中率与长尾。命中率 0%→40% 的收益远大于 60%→80%，规模的边际收益衰减很快，PB 容量是叙事，调度才是真瓶颈；若跨节点搬运要走通用网络，带宽成本可能吃掉全部收益。第三，正确性风险。KV 复用要求前缀逐 token 一致，且模型指纹一致——权重版本、量化格式、RoPE 参数、注意力窗口任何一项变了，缓存就必须整体失效，否则输出静默错乱，属于事故级。第四，场景反转。换到端侧，这套逻辑必须倒过来：没有 PB，只有 8~16GB，策略只能从"扩容"变成"量化 + 淘汰 + 窗口截断"。

### 4. 工程实践

缓存键设计是第一步：模型指纹（权重哈希 + 量化格式 + RoPE/tokenizer 版本）+ 前缀 token 哈希，指纹不匹配直接判 miss，宁可不命中也不能命中错的。落地形态按距离递进：进程内 block pool → 节点内共享内存/本地 NVMe → 集群分层缓存服务。调度上必须做前缀感知路由（prefix-aware routing），让同一前缀落到同一节点，比 round-robin 命中率高一个档位。运维侧四个真问题：一是 SSD 写放大与寿命——缓存是持续大流量写，GC 抖动会直接打穿 P99；二是 KV 读放大，要按 step 维度算带宽账而不是按容量算；三是命中率、TTFT/ITL 分位必须与 miss 风暴的降级路径一起上线，超时即放弃复用、回落重新 prefill；四是缓存不可用必须是"性能降级"而非"服务不可用"，旁路设计是硬要求。

## 架构师点评

一，值得学的是把内存层级当成一等架构维度，而不是把缓存当附属功能。先量测复用率再投资缓存——如果你的负载没有前缀局部性，这套东西一分钱收益都不会有。

二，值得学的是把优化火力对准最贵的资源。前缀复用省下的是 prefill 算力，不是存储 IO。在算力受限的环境里，缓存省的不是时间，是卡，这个换算关系才是投入决策的依据。

三，存疑的是 PB 这个口径。容量叙事容易掩盖真实约束：推理的瓶颈在带宽与调度，而且缓存的边际收益衰减极快。判断这类方案，要问三个数——复用率分布、跨节点搬运走什么互联、miss 惩罚的分位值。

四，存疑的是多租户隔离。共享缓存池如果不按模型/租户物理或逻辑隔离，"不该复用却复用了"会产生极难定位的输出异常，且无法通过常规监控发现。缓存池的隔离等级应与权限等级对齐。

五，可迁移性最强。这套"分层 + 前缀复用 + 前缀亲和路由"的范式，在端侧就是把层级换成 SRAM/DRAM/Flash。把 system prompt 的 KV 固化进 flash 当只读缓存、KV 做 int8/int4 量化、滑动窗口截断，都是同一思想的极端约束版本——做嵌入式推理的团队可以直接把"可复用 KV 落 flash"写进设计约束。

## 延伸思考

如果我来做，第一件事是把缓存从推理引擎里拆出来，做成独立服务：有自己的 SLO、容量模型、淘汰策略和限流，跨引擎（vLLM/SGLang 等）复用。耦合在引擎里的缓存永远只能单点受益，解耦后才能独立扩容。第二件事是离线预热高频公共前缀并持久化——给模型做"权重外挂"，成本极低、收益确定性最高，很多团队跳过了这一步。第三件事是量测先行：上线前采集前缀长度 × 复用次数的分布，命中率低于阈值就不要碰分层缓存。
