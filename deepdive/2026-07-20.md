📌 本期选题：不靠英伟达网卡，国产GPU直通方案实测出炉：吞吐飙升、延迟砍半
📍 原文链接：[量子位](https://www.qbitai.com/2026/07/454932.html)

─── 【为什么选这篇】 ───

大模型推理的瓶颈早已从算力转向互联。NVLink + NVSwitch 是英伟达的护城河，但国产 GPU 没有对应的封闭生态。本文介绍的直通方案尝试绕过标准网卡，在 PCIe/CXL 层面实现 GPU 间低延迟通信，实测吞吐提升、时延降低超过 50%。这对国产推理集群如何组织 tensor parallelism / pipeline parallelism 有直接工程意义。不是产品新闻，而是有实测数据的架构实验，值得拆解。

─── 【核心解读】 ───

**1. 背景与问题**
多 GPU 推理需要频繁交换中间激活和 KV cache partition。标准方案走 TCP/IP 协议栈 + 网卡，无论 RoCEv2 还是 InfiniBand，CPU 都需要参与控制路径，引入上下文切换和协议开销。国产 GPU 普遍没有 NVLink 等价物，只能依赖 PCIe switch 和通用网卡，互联延迟在微秒级，成为跨卡通信的短板。原文提出的直通方案核心是想砍掉网卡这个中间层，让 GPU 之间通过 chiplet 互连或 CXL 内存池直接交换数据。

**2. 设计方案**
具体做法：利用 CXL.mem 协议的共享内存语义，将多个 GPU 的 HBM 地址区域通过 CXL 交换机映射到统一地址空间。推理时，各个 GPU 的 KV cache partition 直接通过 load/store 访问远端内存，不走网卡、不经过 CPU 内存拷贝。方案方（奇异摩尔）是提供 Chiplet 互连 IP 的公司，实测基于国产 GPU + CXL 控制器 + 跨 chiplet 互联的硬件拓扑。吞吐提升来自去掉协议封装和中断处理，延迟减半则是因为跳过了网卡侧的 DMA 队列调度。

**3. 权衡分析**
核心 trade-off：共享内存语义 vs 传统 RDMA。
- 编程模型简化：RDMA 需要显式注册内存区域、处理 QP、管理 WR ID；而 CXL.mem 对上层透明，kernel 可以像访问本地内存一样访问远端 HBM，推理框架无需改动通信代码。
- 代价是隔离性降低：一个 GPU 的错误写操作可能污染另一个 GPU 的 KV cache，故障域从"网卡节点"缩小到"芯片颗粒"。而且 CXL 链路的物理距离受限（通常 <1m），无法像 InfiniBand 做跨机柜扩展，这个方案仅适合同一机箱内的 GPU 集群。
- 如果推理负载是不需要频繁通信的 batch size 1 场景（如 chatbot），直通收益有限；但在 high batch size + tensor parallelism 下，每层都要 all-reduce，收益明显。

**4. 工程实践**
实测数据有吞吐和延迟数据，但缺少最大压力下的稳定性。一个重要隐患是 CXL.mem 的 cache coherency 开销：多 GPU 同时写同一 cache line 时的 snoop 风暴。更现实的部署是每个 GPU 只读远端、只写本地，借助地址映射避免竞争。另外，方案依赖特定 CXL 交换芯片，目前国产化率有限。如果机房内同时有英伟达 GPU 和国产 GPU，直通方案无法与 NVLink 混合使用，需要两层互联叠加。

─── 【架构师点评】 ───

- 可学的设计思路：用硬件共享内存替代网络协议栈，是从根本上降低通信延迟的正确方向——谷歌 TPU 的 ICI 也类似。文章提供了对国产 GPU 生态有参考价值的可行路径。
- 存疑点：共享内存的隔离性在实践中很难保证，推理场景一个 bug 导致坏 write 可能让整卡 HBM 内容损坏，缺少安全机制。
- 可迁移性高：对于边缘推理集群（单机 4-8 卡），CXL 直通能显著降低延迟，值得 SRE 留意该技术在机内拓扑的应用潜力。
- 缺失关键对比：没有与同样不使用网卡的定制方案（如 AMD Infinity Fabric）对比，数据只能说"比用网卡好"，但绝对性能是否接近 NVLink 未知。
- 运维角度：CXL 链路故障的表现与网络故障不同——不是丢包重传，而是总线错误直接 kernel panic，诊断难度大得多。

─── 【延伸思考】 ───

如果我在设计国产推理集群，会选择 CXL 直通作为机内互联底座，但不作为唯一方案。因为跨机通信仍然离不开 RDMA。更实用的做法是混合拓扑：机内走 CXL（低延迟高带宽），机间走 RoCEv2（兼容现有交换机）。推理框架层面需要感知两层互联的延迟差异，自动在 tensor parallelism（机内）和 pipeline parallelism（机间）之间做切分。这一点原文没有提到，但恰恰是部署时最现实的工程问题——写死配置的话，不同批次的服务器配置变化就会导致性能大幅波动。
