## 为什么选这篇

核心矛盾一句话：研究型 Agent 的提案速度已经远超执行算力，"先跑哪个实验"成了比"怎么跑"更昂贵的决策。RPM 把这道决策做成一个廉价、冻结、可部署的前置排序层，是 Agent 编排中"预算分配"的干净样例——不是又一个模型榜单，而是把偏好建模从"对齐人类"移植到"调度计算"。它直击的命题（generator 便宜、executor 昂贵）在实验、CI、评测、AI4Science 里普遍成立，架构思路可整体迁移，值得逐层拆。

## 核心解读

### 1. 背景与问题

研究类 Agent 的产出结构天然失衡：生成假设、组合方法是"一次推理"的成本，验证假设却要吃掉完整训练或评测算力。于是"提案数量 >> 可执行预算"成为必然，瓶颈从生成转移到选择——资源有限时，"先跑哪个"直接决定研究速度与方向。传统解法是代理模型加贝叶斯优化，但它只适用于结构化参数空间；开放语义空间里的实验提案没有核函数可用。RPM 的切入点是让 LLM 的语义判断充当通用 surrogate：在真正执行之前，先对候选实验的相对价值排序。前置概念是 LLM-as-judge 与 verifier 的既有实践，关键差异在于把 judge 从"事后评估结果"前移为"事前选择实验"。

### 2. 设计方案

本质是一个三层漏斗：生成（提案，最便宜）→ 排序（RPM，中等）→ 执行（真实实验，最贵），预算分配在排序层完成。RPM 由 Meta FAIR 联合牛津、UCL 提出，机制上是"研究偏好模型"：用冻结的 LLM 裁判，对一批未执行候选实验（摘要披露的规模在 15 个量级）给出相对排序，调度器按预算取前 k 执行。两个关键决策值得注意。一是输出"偏好排序"而非绝对评分：相对序天然规避跨任务分数漂移，还允许系统在相似提案间做多样性挑选。二是"冻结"：推理期不再训练，部署简单、同输入同输出、可复现，适合作为基础设施版本化。它与 verifier 分工明确——RPM 只做准入控制，最终对错仍由实验结果裁决，因此系统能容忍裁判不完美，只要它显著优于随机选择、且单次成本远低于一次执行。

### 3. 权衡分析

最核心的 trade-off 是"冻结 vs 进化"。冻结换来成本与可复现性，代价是能力天花板：研究前沿快速移动时裁判的"品味"会过期，执行结果也无法回流改进排序。领域稳定（代码审查、工单分流）时冻结是正解；研究域更合理的是低频再蒸馏而非彻底静态。第二个张力在探索与利用：任何学习过的排序器都倾向给"看起来靠谱的增量实验"高分，高方差、高信息量的大胆提案会系统性垫底——若无多样性约束，系统会在语义 plausibility 的局部最优里空转，这在研究场景最致命。第三个是目标错位：裁判按"语义合理性"排序，实验价值却由不可预测的结果决定；若目标是研究加速度，应排序"预期信息增益"而非"预期成功率"。最后是成本边界：只有当裁判成本远低于执行成本时漏斗才成立；候选本身便宜时（小消融），全跑反而更优——该设计只对"执行昂贵"的场景成立，不普适。

### 4. 工程实践

把它当准入控制层运维，三个细节。一是漏斗计量：提案数/通过数/完成数的逐级通过率必须可观测，否则无法判断裁判是太松（执行队列积压）还是太严（误杀好实验）。二是误杀审计：被裁掉的提案按小比例随机放行，既保住探索，又给"裁判错了"提供持续的分母——没有回测的 judge 等于没有测试集的模型。三是反身性：Agent 会学会迎合裁判风格，写出"看起来像好实验"的提案，需盲评、周期性更换裁判或注入扰动，防止提案分布被排序器拉偏。工程上 judge 是同步瓶颈：排序要设延迟 SLO、走异步批排摊薄开销、超时降级为启发式放行；输出应缓存并落审计日志（提案哈希+排序），支撑事后的选择偏差审计。

## 架构师点评

最值得学的不是模型本身，而是"把预算分配从执行后反馈前移到执行前排序"这一编排原语。generator 泛滥、executor 稀缺是通用形态：CI 用例筛选、E2E 冒烟排序、评审 pre-triage、标注预算分配，都能套同一个漏斗。

需要存疑的是偏好信号的来源与校准（报道未披露训练细节）。若排序偏好来自模型自评而非真实执行结果回流，会系统性放大"与主流相似"的提案，形成自我指涉塌缩；没有 ground-truth 支撑的排序器，精度无从谈起。

"冻结"在快速变化的域会过期。更稳的形态是"冻结版本 + 定期离线重蒸馏"，把已执行实验沉淀为持续评估集，每次换版先跑排序质量回归再上线——把模型当发布物管理，而不是当常量。

局限要划清：排序只解决"给定提案里选哪个"，不解决"提案空间够不够多样"。后者需要提案层配合 novelty 机制，否则无论排序器多准，整体都会收敛到局部最优——这是系统级问题。

## 延伸思考

若我来做，会把 RPM 设计成独立的 selection service：对外只暴露 rank(proposals, budget) 一个接口，内部做多裁判集成（不同温度/模型）、多样性采样、ε 比例随机放行，执行结果自动回流成离线评测集，按季度重蒸馏一版灰度上线。原文没提但同样重要的三件事：一是 judge 自身的质量门禁——用已执行实验当 ground truth 持续度量排序精度，而不是默认它好用；二是把输出从"分数"扩展为"分数+不确定性"，高不确定提案送人工或直接放行；三是治理视角——排序偏好一旦固化成基础设施就会自我强化，所以它必须版本化、可审计、可回滚，与任何准入控制层同等对待。说到底，RPM 回答的是"在算力约束下，谁来决定 Agent 的时间花在哪"——这个问题一旦交给模型，就该按生产系统来管。
